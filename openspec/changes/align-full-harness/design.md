# 完整 Harness 设计

## Context

项目是 pnpm monorepo，业务为 React H5、NestJS、TypeORM、PostgreSQL。11 月 24 日复核确认本地完整验证通过，GitHub 的 Windows 基础作业在数据库文档校验阶段失败，主分支检查未受保护。

## Goals / Non-Goals

目标是有实际知识、可执行工具、隔离资源、诊断查询、维护补丁和演练证据的完整闭环。业务接口及数据库结构保持兼容，Git 发布仍由用户控制。

## Decisions

- OpenSpec 由 AI 维护，承载正式行为规范和执行计划。用户在 `docs/product/` 维护业务原稿，有原稿时提案直接记录来源。
- 知识总索引链接原稿目录、正式规范、活动变更、归档和技术债。原稿目录可达时，其所有手写 Markdown 均可直接从目录查找，仓库内链接仍参加校验。
- 生成工具只处理数据库结构文档。源码指纹用于随实现维护的工程知识，手写需求原稿独立于实现变化。
- 数据库文档通过临时 PostgreSQL 重放迁移并读取 catalog 生成，校验模式不写已跟踪文件。
- 每个实例用运行编号拥有数据库、上传目录、API、Vite 和 LGTM 容器，Docker 随机映射回环端口。
- Node OpenTelemetry 在 Nest/TypeORM 前初始化，适配 ESM hook；采集 HTTP/pg 和业务 span，日志以相同上下文关联。
- 健康接口仅在 Harness 模式启用，敏感字段不写遥测。观测容器限制 2 GiB，启动失败清理已创建资源。
- 维护工作区采用当前源文件快照覆盖临时 detached worktree；补丁相对快照生成，主索引与用户分支保持原状。
- 原生本机自动化调用维护技能，周一至五 09:00，最多一个问题、两轮修复和三十分钟，交付本地补丁和报告。
- CI 汇总 Windows 和 Ubuntu 基础、真实数据库、Chromium 和隔离遥测作业。汇总作业仅依赖作业结果，便于固定为必需检查。当前私有仓库套餐先执行按 PR、准确提交和人工审批的合入约定。
- 数据库文档由真实迁移生成和校验。GitHub 托管 Windows 使用管理员权限启动子进程，PostgreSQL 拒绝启动。Windows CI 复用基础步骤中无需数据库的部分，Ubuntu CI 继续执行包含生成文档校验的基础验证。本地基础和完整入口继续校验真实生成结果。
- 后端业务模块从公开入口向外提供装配、守卫或查询。分类通过自身 ORM 关联读取商品计数，菜品通过分类服务校验，订单通过菜品模块查询下单快照并沿用原事务。数据库注册、CLI 导入和 ORM 关联保留点对点例外。用类型导入和明确的实体目标消除 ORM 运行时导入环。
- 架构检查复用工作区解析过的源码依赖，限制跨模块入口并拒绝运行时循环。规范检查读取固定版本 OpenSpec 的结构化校验结果，将归档冲突作为失败；以正式规范为基线移除已同步的历史增量。
- 质量页记录任务首次验收、验收后的实质返工、人工干预及可取得的成本。技术债记录优先级、处理方向和验收条件。周期维护保留当前暂停记录，恢复需要明确授权。

## Risks / Trade-offs

隔离双实例继续使用实际数据库和容器验收。真实 PostgreSQL 回归覆盖分类计数、删除限制、菜品上下架和订单事务。CI 汇总仍要求两端基础验证全部通过，生成文档校验故障由 Ubuntu 基础作业反馈。远端验收按实际提交记录。
