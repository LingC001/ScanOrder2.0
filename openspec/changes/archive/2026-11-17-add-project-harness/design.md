# 工程 Harness 设计

## Context

现有仓库使用 Node.js 24、pnpm 11.5.1，包含前端、API、共享包以及隔离 PostgreSQL／Playwright 测试。Windows 已有全局 OpenSpec 1.5.0 和用户级旧提示词，需使用项目依赖保证本地与 CI 一致。

## Goals / Non-Goals

目标：用简短入口导航知识，机械约束关键边界，统一失败反馈，支持 OpenSpec 计划到归档。首轮仅建立工程规范，业务规范随后续需求补齐。

范围外：业务功能扩展、数据库改造、自动提交／推送、修改远端分支保护和用户全局工具配置。

## Decisions

- 根指引作为导航，细节放局部指引和知识库，避免重复大段上下文。
- 本地固定 OpenSpec 2.1.0，结构由 CLI 初始化；项目中文技能按标准流程适配，避免新版初始化清理用户级旧提示词。
- 架构检查使用 TypeScript AST 和模块解析，识别导入、再导出和动态导入，校验公开入口及平台边界；不对 TypeORM 的合法实体关系施加全局无环要求。
- Markdown 链接使用解析器识别引用与代码块，YAML 用解析器处理配置与技能元数据；仅检查仓库本地目标，不请求外链。
- 验证编排以现有脚本为执行单元，逐项记录退出码、耗时和错误。失败即停止，报告写忽略目录，避免生成记录污染源码。
- CI 基础验证覆盖 Windows／Ubuntu，数据库和浏览器在 Ubuntu 单独作业运行，复用已有隔离数据库脚本。
- 文档和规则检查、执行编排的测试使用临时项目与真实子进程，覆盖成功和失败行为。

## Risks / Trade-offs

- 中文技能为项目定制，升级前应在临时目录检查差异，不能盲目用上游生成结果覆盖。
- 文档检查验证结构与链接，不推断文档和代码的语义一致性。
- TypeScript 解析覆盖可静态识别的模块引用，不能推断运行时拼接导入；类型和真实链路测试补充行为验证。
- 本次可以验证本地 Windows，Ubuntu 与远端 CI 结果必须在实际运行后记录。
