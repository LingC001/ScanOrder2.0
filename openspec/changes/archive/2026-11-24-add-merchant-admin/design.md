# 商家后台技术设计

## Context

当前 `apps/web` 只有宽度受限的移动端路由，`apps/api` 的菜品仍以分类字符串保存，订单查询无身份边界且创建后直接标记完成。数据库由显式迁移管理，测试使用隔离 PostgreSQL。方案需沿用 NestJS 模块边界、共享契约和现有图片存储能力。

## Goals / Non-Goals

**Goals:**

- 在同一 Vite 应用中提供响应式 `/admin`，与移动端点餐路由共用 `src/api.ts` 和公开共享类型。
- 以服务端会话和数据库约束保证商家、顾客及订单数据边界。
- 通过可回滚迁移转换现有分类、商品和订单数据，不改变商品 UUID 与订单快照。
- 保持旧菜单导入的预检、事务、幂等和图片复用行为。

**Non-Goals:**

- 不实现顾客注册、多商家隔离、员工账号、支付或退款。
- 不引入新的 Web 框架、UI 组件库或身份服务。

## Decisions

### 独立账号会话

使用 PostgreSQL `sessions` 表保存随机令牌的 SHA-256 摘要、主体类型、主体标识及过期时间。浏览器只持有 `HttpOnly`、`SameSite=Strict` 的商家或顾客 Cookie。商家与顾客守卫均由服务端读取 Cookie 查询有效会话，注销时删除对应记录。

商家凭据来自 `ADMIN_USERNAME` 和 `ADMIN_PASSWORD_HASH`，哈希格式为 `scrypt$<salt>$<hex>`。登录失败限制保存在单进程内存中，默认同一来源十分钟最多五次失败。固定顾客入口由 `CUSTOMER_LOGIN_ENABLED` 控制，账号标识来自 `CUSTOMER_ACCOUNT_ID`。开发环境提供显式示例配置，生产部署应替换。

不采用无状态签名 Cookie，因为主动注销无法及时失效。不引入 Passport，因为只有两个固定主体且项目无需额外身份策略。

### 分类与商品模型

新增 `categories` 表和 `FoodEntity.categoryId` 外键。分类按 `sortOrder, name` 排序，名称唯一。商品状态使用 `active`、`inactive`、`archived`，新增和恢复后为 `inactive`。归档不删除记录，避免破坏订单外键与历史图片引用。

管理员商品接口使用分页 DTO 和 multipart 表单，复用现有图片服务。更新图片只创建新文件，不移除既有文件，以保证订单快照中的图片持续可用。旧菜单导入先按名称查找或创建分类，再按 `legacyId` 更新商品；重导不覆盖已有分类归属、上下架或归档状态。

### 订单状态与归属

订单新增可空 `customerId` 和非空 `status`，状态为 `pending`、`accepted`、`completed`、`cancelled`。创建订单从顾客会话取得归属并保存为 `pending`。迁移把旧订单的 `finished=true` 转为 `completed`，`false` 转为 `pending`，并保持 `customerId` 为空，因此旧订单只在商家后台可见。

状态更新在数据库事务中锁定订单行，并根据当前状态校验允许的目标状态。顾客列表和详情始终附加本人 `customerId` 条件，查不到时返回 404，避免泄露订单是否存在。

### 路由与页面

移动端保留现有路由并使用独立宽度容器，首次加载通过顾客会话状态显示固定账号登录窗。`/admin` 使用响应式桌面布局，登录后提供商品、分类和订单三个页面。原 `/upload` 路由、页面、公开创建菜品接口和旧公开订单列表接口移除。

后台使用当前 Tailwind、Lucide 和共享类型。列表提供加载、空结果和错误状态，表单失败保留输入。未使用设计稿，因此不引入外部视觉参照。

### 数据迁移

新增单个显式迁移：创建分类，按现有商品分类文字回填，添加商品分类外键和状态；增加订单状态及顾客归属；创建会话表。部署前备份数据库和上传目录，停止写入后运行迁移。回滚迁移会按分类名称还原商品字段并依据订单状态还原 `finished`，但回滚后新会话与后台专属字段不可继续使用。

## Risks / Trade-offs

- 单进程登录限流在重启后清空，也无法跨多个 API 实例共享 → 当前单实例部署可接受，后续多实例时迁移到共享存储。
- 固定顾客账号意味着知道入口的人可查看该账号全部订单 → 部署配置可关闭入口，产品已确认用于单人场景。
- `.env.example` 中的开发凭据可被复制到生产 → 启动文档明确要求替换，并提供生成哈希的命令而不记录生产口令。
- 分类删除与商品更新可能并发 → 数据库外键拒绝仍有商品的分类删除，服务层统一转换为可读的 409 响应。

## Migration Plan

1. 备份 PostgreSQL 与 `UPLOAD_DIR`，部署前停止菜单及下单写入。
2. 配置商家凭据和固定顾客入口，构建并执行数据库迁移。
3. 启动 API 与 Web，使用管理员登录核对分类数量、在售商品和后台订单。
4. 失败时回退应用版本并执行新迁移的 `down`，再按备份恢复图片目录。
